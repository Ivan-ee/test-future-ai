# test-future

Прототип «предсказателя будущего» — системы краткосрочных криптопрогнозов
(24ч, вверх/вниз) с прозрачной логикой: какие данные взяли, как проанализировали,
какие цифры сошлись и почему система пришла к выводу.

> Это прототип. Приоритет — прозрачность логики и демонстрируемость
> («цифры сходятся»), а не предсказательная сила. Прогноз может быть часто
> неверным — это нормально; главное, что система честно показывает точность
> и объясняет ошибки.

---

## Быстрый старт

```bash
cp .env.example .env       # при необходимости отредактируйте порты/ключи
make dev                   # бэкенд :8081 + фронтенд :3001
```

- Главная страница: http://localhost:3001 — 5 монет с ценами и прогнозами.
- API: http://localhost:8081/api/assets
- Health: http://localhost:8081/api/health

При холодном старте (пустая БД) worker сразу наполняет базу: через ~1 минуту
на главной появляются 5 монет с ценами, индикаторами и первыми прогнозами.

### Что нужно

- Go 1.25+
- Node.js 18+ (для фронтенда)
- (опционально) `OPENAI_API_KEY` — для сентимента новостей. Без ключа прогноз
  работает на 3 факторах.

## Как считается прогноз

Прогноз — это детерминированная функция от 4 факторов. Никакого ML в ядре —
только арифметика. Чистые функции в `internal/scoring` полностью покрыты тестами.

### Шаг 1. Технические индикаторы (из рядов цен)

Из `price_points` за 30 дней считаются индикаторы (`internal/indicator`):

| Индикатор | Период | Что измеряет |
| --------- | ------ | ------------ |
| RSI       | 14     | Перекупленность/перепроданность (формула Уайлдера) |
| ROC       | 10     | Скорость изменения цены, % |
| SMA       | 7, 20  | Скользящие средние (кроссовер) |
| VolumeSignal | 14  | Отношение объёма к среднему |

### Шаг 2. Сигналы факторов [-1..1]

Каждый индикатор → сигнал в диапазоне `[-1..1]` (`scoring/signals.go`):

| Фактор | Откуда сигнал | Логика |
| ------ | ------------- | ------ |
| **RSI** | RSI(14) | RSI≥70 → вниз (перекупленность); RSI≤30 → вверх (перепроданность); 50 → 0 |
| **Momentum** | ROC(10) + SMA(7)/SMA(20) | Среднее: tanh(ROC/5) и tanh(crossover×10) |
| **Volume** | VolumeSignal(14) | Выше среднего → слабый вверх; ниже → слабый вниз; норма → 0 |
| **Sentiment** | средний сентимент новостей за 24ч | Тождественен значению [-1..1] (опц., нужен OpenAI) |

### Шаг 3. Веса и scoring

Базовые веса факторов (`scoring.DefaultBaseWeights`):

| Фактор    | Базовый вес |
| --------- | ----------- |
| RSI       | 0.25        |
| Momentum  | 0.35        |
| Volume    | 0.15        |
| Sentiment | 0.25        |
| **Сумма** | **1.00**    |

Веса нормируются под сумму присутствующих факторов (если нет sentiment — под
0.75). Веса могут адаптироваться (см. раздел ниже) — тогда используется
`adjusted_weight` вместо базового.

Формула прогноза:

```
raw_score  = Σ(signal_i × adjusted_weight_i)          # по всем факторам
direction  = raw_score ≥ 0 ? "up" : "down"
confidence = 0.5 + |raw_score|/2 − contradiction_penalty
```

`contradiction_penalty`: если 2+ фактора смотрят против итогового направления —
каждый штрафует confidence на 0.05. Confidence зажат в `[0.5, 1.0]`.

## Численный пример (проверьте сами)

Сигналы факторов ниже взяты как данные — это выходы шага 2 (преобразование
индикаторов в `[-1..1]`). Возьмём сценарий: RSI=40 (перепроданность → вверх),
моментум умеренно вверх, объём в норме, новости негативные.

### Входные сигналы

| Фактор    | Signal | Откуда (индикатор → сигнал)                |
| --------- | ------ | ------------------------------------------ |
| RSI       | +0.50  | RSI=40: `(50−40)/(70−50)` = 0.5 (вверх)    |
| Momentum  | +0.30  | ROC>0 и SMA7>SMA20 → вверх                 |
| Volume    |  0.00  | объём в норме → нейтрально                 |
| Sentiment | −0.40  | средний сентимент новостей за 24ч          |

### Расчёт вкладов (contribution = signal × adjusted\_weight)

Сумма базовых весов 4 факторов = 1.00, поэтому после нормировки
`adjusted_weight = base_weight` (каждый вес делится на сумму 1.0).

> Примечание про адаптацию: `adjusted_weight` здесь — это вес **после
> нормировки** под сумму присутствующих факторов. Адаптация весов через EMA
> (раздел ниже) применяется в worker **до** вызова `Forecast` и подменяет
> базовые веса; в этом примере статистики ещё нет, поэтому EMA=0.5 и множитель
> адаптации = 1.0 — веса не меняются.

| Фактор    | Signal | Weight | Contribution             |
| --------- | ------ | ------ | ------------------------ |
| RSI       | +0.50  | 0.25   | +0.50 × 0.25 = **+0.1250** |
| Momentum  | +0.30  | 0.35   | +0.30 × 0.35 = **+0.1050** |
| Volume    |  0.00  | 0.15   |  0.00 × 0.15 = **+0.0000** |
| Sentiment | −0.40  | 0.25   | −0.40 × 0.25 = **−0.1000** |

### Итог

```
raw_score = 0.1250 + 0.1050 + 0.0000 − 0.1000 = +0.1300
```

`raw_score ≥ 0` → **direction = "up"** (вверх).

```
base_confidence = 0.5 + |0.1300|/2 = 0.5 + 0.0650 = 0.5650
```

Противоречит направлению "up" только sentiment (signal < 0) — это 1 фактор.
Штрафа нет (нужно ≥2 противоречащих).

```
confidence = 0.5650  →  метка «низкая уверенность» (< 0.65)
```

**Результат: прогноз «вверх», confidence ≈ 0.57.** Система так и скажет в
`argument_text`: перечислит факторы и итог с уровнем уверенности.

> Эти числа воспроизводятся дословно, если вызвать `scoring.Forecast` с теми же
> сигналами. Формула `raw_score = Σ(signal × adjusted_weight)` проверяется
> юнит-тестом `TestForecast_RawScoreEqualsWeightedSignalSum` в
> `internal/scoring/scoring_test.go`.

## Как система понимает, что ошиблась

Прогноз создаётся в статусе `active`. Через 24ч (горизонт) resolve-цикл сверяет
его с фактом. Это замкнутая петля обучения — система становится точнее со
временем. Полная диаграмма — в [docs/architecture.md](docs/architecture.md).

### 1. Resolve — сверка с фактом

```
change% = (цена_сейчас / цена_на_момент_прогноза − 1) × 100
```

| Результат  | Условие                                  |
| ---------- | ---------------------------------------- |
| **hit**    | направление совпало и \|change\| ≥ 0.5%  |
| **miss**   | направление не совпало и \|change\| ≥ 0.5% |
| **neutral**| \|change\| < 0.5% (слишком маленькое движение, не учитывается) |

Результат пишется в `outcomes` с ценами и `price_change_pct`.

### 2. Атрибуция — кто «виноват»

При **miss** система находит фактор с максимальным `|contribution|`, чей знак
противоречит фактическому направлению — это «виновный» фактор
(`outcomes.culprit_factor`). Человекочитаемое объяснение — в
`culprit_explanation`, например: *«momentum давал +0.1750 (сигнал вверх, 0.50),
но цена упала — фактор увёл прогноз в сторону»*.

При **hit** находится ведущий фактор (макс согласующийся вклад) — главный
драйвер точного прогноза.

### 3. Адаптация весов — система учится

Для каждого фактора по монете ведётся `factor_stats.hit_rate_ema` —
экспоненциальное среднее доли совпадений знака сигнала с фактом (α=0.2):

```
EMA_new = 0.8 × EMA_old + 0.2 × (знак сигнала совпал с фактом? 1 : 0)
```

Старт — 0.5 (нейтрально). При следующем прогнозе вес фактора адаптируется:

```
adjusted_weight = base_weight × clamp(EMA / 0.5, 0.5, 1.5)
```

| EMA   | Множитель | Эффект                          |
| ----- | --------- | ------------------------------- |
| 1.0   | 1.5       | Фактор часто угадывает → повышение |
| 0.5   | 1.0       | Нейтрально (старт)              |
| 0.0   | 0.5       | Фактор часто ошибается → понижение |

Neutral-исходы не учитываются — слишком маленькое движение не несёт сигнала.

### Что видит пользователь

- **`GET /api/accuracy`** — глобальная сводка: точность за последние 100
  сверкнутых прогнозов, средняя заявленная уверенность vs фактическая точность,
  per-factor hit-rate.
- **`GET /api/forecasts/{asset}`** — история прогнозов по монете с результатами
  сверки (hit/miss/neutral) и «виновником» промаха.
- На главной — виджет точности (`AccuracyWidget`).

## Что использовано из ИИ

**Единственное применение ИИ — оценка сентимента новостей через OpenAI**
(`internal/sentiment`). Берётся батч заголовков+lead новостей, модель возвращает
`score [-1..1]` и короткое summary на русском. Результат — 4-й фактор прогноза.

Всё остальное — детерминированная логика на чистом Go: индикаторы (формулы),
scoring (линейная комбинация), resolve/атрибуция/адаптация (арифметика).

Без `OPENAI_API_KEY` сентимент выключен — прогноз считается по 3 техническим
факторам (graceful degradation, веса перенормируются). Кэш по `sha256(title+body)`
исключает повторные запросы за тот же текст.

## Архитектура

Подробно — в [docs/architecture.md](docs/architecture.md). Кратко:

```
источники → SQLite → индикаторы → scoring → прогноз → HTTP API → Next.js UI
                                                              │
resolve (24ч) → атрибуция → адаптация весов → следующий прогноз ◄┘
```

Один процесс: HTTP-сервер и worker-цикл (3 тикера) в горутинах, общая БД.
Graceful shutdown по SIGINT/SIGTERM.

### Схема БД (кратко)

| Таблица               | Назначение                                  |
| --------------------- | ------------------------------------------- |
| `assets`              | 5 отслеживаемых монет                       |
| `sources`             | Реестр источников (coingecko, coinpaprika…) |
| `price_points`        | Точки цен (дедуп по asset+ts+source)        |
| `indicator_snapshots` | Последние индикаторы по монете (1 строка)   |
| `news_items`          | Новости (дедуп, сентимент nullable)         |
| `forecasts`           | Прогнозы (active → superseded/resolved)     |
| `forecast_factors`    | Декомпозиция вклада факторов                |
| `outcomes`            | Результаты сверки (hit/miss/neutral)        |
| `factor_stats`        | hit\_rate\_ema по фактору×монете            |
| `update_log`          | Журнал циклов fetch                         |

Полная схема — `internal/db/schema.sql` (применяется автоматически при старте).

## Smoke-тест

Ручная проверка «с нуля до работающего UI»:

```bash
make clean          # удалить БД и артефакты
make smoke          # поднимает бэкенд, ждёт наполнения, проверяет API, останавливает
```

Или вручную:

1. `make clean && make dev`
2. Через ~1 минуту открыть http://localhost:3001 — главная показывает 5 монет
   (BTC, ETH, SOL, BNB, XRP) с ценами.
3. Кликнуть по монете — карточка открывается, видны индикаторы и прогноз
   (направление ↑/↓, confidence, факторы).
4. `curl http://localhost:8081/api/forecasts | jq` — прогнозы по всем монетам.
5. В логе бэкенда нет ошибок (`worker:` строки — норма).

Ожидаемый результат: 5 монет с ценами, прогнозами по 4 (или 3 без OpenAI)
факторам; точность начнёт копиться после первых resolve-циклов (через 24ч).

## Тестирование

Тесты сосредоточены на чистой логике (без моков сети/БД/LLM), согласно
тестовой стратегии проекта:

- `internal/scoring` — ядро прогноза: direction, confidence, нормировка весов.
- `internal/accuracy` — resolve, атрибуция, адаптация весов.
- `internal/indicator` — RSI/ROC/SMA/VolumeSignal на эталонных рядах.
- `internal/source/*` — маппинг ответов API в доменные модели.
- `internal/storage` — дедуп `price_points` (in-memory SQLite).
- `internal/worker` — сквозной путь источник→БД→прогноз с фейковыми источниками.

```bash
make test              # все тесты
go test -v ./...       # подробный вывод
```
